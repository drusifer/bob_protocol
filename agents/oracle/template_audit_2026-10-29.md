## Scope and summary

At the audit baseline, reviewed every file in `agents/templates/` (16 files), its counterpart in `bobp/templates/agents/templates/`, the catalog in `ARTIFACTS.md`, and each rubric block; the directories matched. The accepted recommendations are now implemented in the packaged source and copied to the live directory.

The artifact families are sensible, but their conventions have grown independently. Several templates repeat lifecycle instructions already owned by skills; examples are sometimes written as mandatory requirements; and the review rubric system is heavier than the user's requested KISS pass/fail model. The goal should be **one canonical rule per concern, optional detail where the artifact type calls for it, and a small observable pass/fail check for every template**.

## Implementation Status

Applied the recommendations to all 16 canonical files in `bobp/templates/agents/templates/` and synchronized all 16 files to `agents/templates/`. The changes establish one binary PASS/FAIL check per template, including catalog, chat, state, TLDR, and both language-specific SDLC inserts. The SDLC language files are now compact profiles instead of duplicate full guides. Other substantive fixes include generated chat format, uv dependency groups, manager-specific JS commands, risk-based test strategy, optional DDD/research/UAT detail, lesson cause, story/task traceability, and consistent UAT results.

Validation: source/live directory equality, one check marker pair per file, and `git diff --check` all pass. No tests were run because these changes only affect documentation. The revised checks have not yet been calibrated against a sample of completed project artifacts; reviewers should report ambiguous criteria for follow-up.

## Cross-template conventions

Adopt these conventions across the set:

1. Start with one descriptive H1, a one-paragraph purpose/scope, and only useful metadata (owner, status, date, related artifact IDs). Avoid repeating ownership and workflow prose inside both template comments and the document body.
2. Use consistent `{placeholder}` notation. Mark examples as examples, and mark optional sections explicitly. Use `N/A — reason` only where the reason affects a reviewer or downstream user.
3. Keep a single source of truth for process rules. Templates should link to the owning skill for gates, persona responsibilities, command invocation, state handling, and lifecycle; they should describe the artifact's content.
4. Separate related artifact roles: architecture describes a system/design; an ADR records one decision; a test strategy describes the project's risk-based approach; a UAT plan records specific acceptance scenarios and results; stories express outcomes; the task board schedules implementation work.
5. Each template ends with a short rubric/checklist that tests only that artifact's purpose. Use binary criteria: `PASS` or `FAIL`, with `N/A` plus a reason where appropriate. A failure names the missing or contradictory evidence and the smallest correction. No Strong tier, percentage, score, or fixed criterion count is needed.
6. Make mirror updates part of the same change: edit the live `agents/templates/` source and packaged counterpart, then verify equality. A future sync check should fail when copies drift.

## Rubric audit

At the audit baseline, twelve templates had W/A/S tables and four lacked artifact-specific checks: `ARTIFACTS.md`, `_template_CHAT.md`, `_template_state.md`, and `_template_tldr.md`. Implementation converted or replaced all 16 with binary checks.

The current rubric policy in `ARTIFACTS.md` requires 4–6 criteria, three rating levels, independent reviewers, three-example calibration, and verdict syntax. That conflicts with the requested KISS option and creates substantial repeated text. The rubrics are usually specific, but several fail completeness or independence:

- `ARCH`: `USER` can judge interface usability that may be outside an architecture document; `FEAS` overlaps the separate SDLC artifact.
- `DOMAIN`: `BOUND` Strong asks for a context map absent from the body; `EVENT` may be inapplicable but its row does not clearly grant N/A.
- `FINDING`: `TRADE` permits N/A in the row, while the body still requires an alternatives table.
- `LESSON`: `CAUSE` has no corresponding named prompt in the body.
- All SDLC variants repeat the same rubric; its six criteria overlap `TRUE`/`CLEAN` and `WHOLE`/`CHECK` in places.
- `TEST_STRATEGY`: rubric rewards unsupported proportions and prescriptive role routing instead of verified project-specific risks and gates.
- `UAT`: `EVID` rewards timestamps/commit hashes that may not be useful evidence for each scenario.
- `USER_STORIES`: `SIZE` treats points as mandatory, while points are a planning convention rather than a necessary property of a user outcome.

Recommended rubric contract: 3–6 **binary** criteria per artifact, each with a direct question and a testable pass condition. A fail should identify the evidence that is missing, contradictory, or unsupported. Allow `N/A` only when that condition truly does not apply and the author records why. For state/chat/TLDR and the catalog, use mechanical integrity checks where possible rather than prose-heavy review tables. Keep the rubric with the template and remove it from instantiated artifacts.

## Research and examples

The recommendations draw on established artifact patterns, not one universal template. Standards should be adapted to project size and purpose; optional sections are better than requiring irrelevant content.

| Artifact family | Reference and useful pattern |
|---|---|
| Architecture | [arc42 documentation](https://arc42.org/documentation/) treats architecture as a set of views and quality goals, and supports docs-as-code. The [C4 model](https://c4model.com/diagrams) says context and container views are sufficient for many teams; component/code views are added when useful. This supports a lean, audience-driven architecture template rather than mandatory diagrams at every level. |
| Decisions | [MADR](https://github.com/adr/madr) provides full and minimal variants around context, drivers, options, outcome, and consequences. Its template makes confirmation optional and keeps each decision in a separate record. This is a better base than duplicating consequences and option pros/cons. |
| Domain model | Microsoft's [bounded-context guidance](https://learn.microsoft.com/en-gb/dotnet/architecture/modern-web-apps-azure/architectural-principles) emphasizes that each context owns its concepts/language and can evolve independently. The template should capture context boundaries and language first; tactical DDD structures should be included only when discovered and relevant. |
| User stories and acceptance | [Agile Alliance's INVEST checklist](https://agilealliance.org/glossary/invest/), [Cucumber's Gherkin reference](https://cucumber.io/docs/gherkin/reference/), and [GOV.UK user-story guidance](https://www.gov.uk/service-manual/agile-delivery/writing-user-stories) focus on valuable outcomes, testability, and observable acceptance. None requires every backlog item to use one sentence format or every story to have a negative-path criterion. |
| Test strategy | The [ISTQB CTFL syllabus](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf) distinguishes entry/exit criteria and emphasizes risk, test basis, resources, environments, and measurable completion. This favors explicit project risks and gates over a universal 70/20/10 test-count split. |
| UAT/usability | [GOV.UK moderated usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing) frames sessions around actual or likely users attempting specific tasks. Keep those observations distinct from scripted acceptance tests with fixed commands and exit codes. |
| Lessons/incident learning | Google's [SRE postmortem practices](https://sre.google/workbook/postmortem-culture/) emphasize blameless causal analysis and owned, verifiable action items. The lesson template should preserve the cause-to-rule relationship and link evidence, without turning every small engineering lesson into a full incident postmortem. |
| Markdown and template size | Google's [documentation style guide](https://google.github.io/styleguide/docguide/style.html) favors minimal, fresh, portable, readable docs and recommends keeping syntax simple. Its “minimum viable documentation” principle supports short templates with conditional sections and concise checks. |
