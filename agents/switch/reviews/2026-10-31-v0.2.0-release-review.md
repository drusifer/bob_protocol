## Scope and Threat Model

- **In scope / out of scope:** Changed Python (`chat_diagram.py`), `Makefile` (security and release targets), `.githooks/pre-commit`, both GitHub workflows, dependency locks. Out of scope: the Codex/Promptfoo eval runtime beyond the audit, and the PyPI/GitHub account settings other than the `pypi` environment's reviewer rule.
- **Assets worth protecting:** The `bobp` PyPI project and release integrity, the repo contents (no secrets expected), and users who install the package.
- **Entry points and trust boundaries:** `CHAT.md` text into the diagram generator; GitHub Actions and third-party actions in the publish job; the local `gh`/git credentials used by `make release`.
- **Threats considered:** Tampering (compromised action or dependency), Information disclosure (secret committed), Elevation of privilege (default token scope), Spoofing/Repudiation (not applicable: no auth or user-facing service), Denial of service (SEC-001, dev-only).

## Method and Coverage

- **Reviewed by:** Read the changed code and workflows; traced chat text into the Markdown output and reproduced it.
- **Tool results:** `gitleaks` 8.26.0 `detect --source .`: 84 commits, no leaks. `pip-audit` on the exported `uv.lock`: no known vulnerabilities. `npm audit --audit-level=high` on the persona-eval lockfile: fails (SEC-001). All via `bobp make security-scan-*`. `gh api` confirmed the `pypi` environment has required reviewers.
- **Not covered:** GitHub repository default-token permissions and branch protection (settings not inspected); Mermaid tool dependencies (no lockfile); runtime behavior of the Codex SDK eval runner.

## Root Causes and Recommendations

CI and release automation predate the security tooling, so they lack the pinning and scanning the local tools now provide. One systemic fix: bring the workflows up to the repo's own security skill (pin, least privilege, scan).
